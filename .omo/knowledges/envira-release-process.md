# Releasing envira (as done for 0.1.3, 2026-11-05)

## Steps

1. Bump `version` in `Cargo.toml`, then `cargo check` to refresh `Cargo.lock`. Nothing else
   carries the version: `pyproject.toml` takes it from Cargo.toml (`dynamic = ["version"]`), and
   the `0.1.2` strings in `src/selfupdate.rs` are test data.
2. `cargo test`, `cargo run -- --version`, commit `chore: release X.Y.Z`, push main.
3. `git tag -a vX.Y.Z -m "envira X.Y.Z"` on that commit, `git push origin vX.Y.Z`.
   - The `version` job fails the run when the tag does not match Cargo.toml.
4. The tag run of `release.yaml` runs every test again, then:
   - `publish`: PyPI wheels;
   - `crates`: crates.io;
   - `release`: the GitHub release with the binaries, `.sha256` files and `catalog.toml`;
   - `verify`: pip install on ubuntu, ubuntu-arm and macOS;
   - `verify-crate`: cargo install and cargo binstall.

   The full run takes about 10 minutes.

5. Write the release notes. CI creates the release with only the "Full Changelog" link, and
   0.1.3 to 0.1.5 went out like that until they were filled in afterwards. Sections follow
   v0.1.1/v0.1.2 (`## TUI`, `## Fixes`, …), are written for users, and keep the Full Changelog
   line. Publish them with `gh release edit vX.Y.Z --notes-file notes.md`.
6. Before tagging, check that the integration scripts (`tests/integration/*.sh`) do not grep
   for wording that changed. 0.1.5's first tag failed on macOS because `macos.sh` looked for
   the old skip reason `os:linux`, so nothing was published. The tag was moved to the fixed
   commit (delete it on the remote, tag again, push), which is safe only while nothing has
   been published.

## Checking that it went out

```bash
gh release view vX.Y.Z --json assets --jq '.assets[].name'
curl -s https://pypi.org/pypi/envira/json | python3 -I -c 'import json,sys; print(json.load(sys.stdin)["info"]["version"])'
curl -s -A envira-release-check https://crates.io/api/v1/crates/envira | python3 -I -c 'import json,sys; print(json.load(sys.stdin)["crate"]["max_version"])'
```

- The website's `envira/catalog.toml` should equal the release's `catalog.toml`.
- CI prepends a `# Generated by ...` line, so a local `envira --no-remote catalog show` differs
  from it only by that line.
- Run any local envira with the scratch state/config dirs, never against the real ones.

## Known noise

- `release-web` (the force-push of the `dist` branch for boot.controlnet.space) runs for both
  the main push and the tag push of the same commit, so one failure is covered by the other.
- In 0.1.3 the tag run's push failed with GitHub's `fatal error in commit_refs`, while the main
  run's deploy of the same commit succeeded. Plain `git push` got HTTP 500 the same afternoon;
  a retry went through.
